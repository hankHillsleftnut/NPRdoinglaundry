Spec:
- `Platform/LaunchOptions.swift`:
  ```swift
  extension Platform {
      struct LaunchOptions: Sendable, Equatable {
          enum DataSource: String, Sendable { case live, sample }
          var dataSource: DataSource          // -Data live|sample   (default live)
          var environment: Backend.Environment // -Environment production|staging|local (default production)
          var screen: String?                 // -Screen JR-1       (read by the UI engineer's launcher)
          var state: String?                  // -State empty|offline|…   (read by the sample data)
          var account: String?                // -Account fresh|day-one|month  (a seeded staging account, local/staging only)
          static var current: LaunchOptions { get }   // parses ProcessInfo.processInfo.arguments
          static func parse(_ arguments: [String]) -> LaunchOptions
      }
  }
  ```
- **Release builds ignore every option** and always return `.live` / `.production`: the parse is compiled only under `#if DEBUG`, with the release path returning the constant (no runtime check that a release build could take). TestFlight builds are release builds, so environment switching on TestFlight goes through PL1.1's hidden developer setting, not launch arguments.
- `Platform.Environment.live(launch:)` uses `dataSource` to choose each flow's data implementation: `.sample` uses the UI engineer's `Sample…Data(state:)`, `.live` uses ours. Until a flow has a `Live…` type, `.live` falls back to sample and logs `Platform.Log.Event.flowNotLiveYet(flow:)` once.

Steps: type → parse → wire into `live(launch:)` → tests → PR.

Acceptance: launching with `-Data sample -State empty` gives the sample implementation with that state; no options gives live/production.

Tests (layer 5): "no arguments means live data on production"; "-Data sample -State offline is parsed"; "an unknown value falls back to the default and is reported"; "a release build ignores every option" (test the release parse function directly).

Proof in the PR: test output.

Watch out: the UI engineer owns `-Screen` handling (which view opens); you only parse and hand it over. Keep argument names exactly as testing.md lists them.
